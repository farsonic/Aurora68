Aurora68 0.4 - a Macintosh SE build that also boots System 7 on a Pi alone
==================================================

What this is
------------
Aurora68 puts a Raspberry Pi in a Macintosh SE's 68000 socket on a classic PiStorm board and
runs the Macintosh IIci ROM on it: a 68040 to the Mac, memory on the Pi, a second screen on
the Pi's HDMI, disks on the Pi, WiFi, and the SE's own screen, keyboard, mouse, SCSI and
floppy kept. 0.3 is the first build meant for the hardware: a classic PiStorm (the DIP-64
board with the EPM240 CPLD, stock firmware) and a Raspberry Pi 3A+, Zero 2 W, 3B or 3B+
("Which Raspberry Pi", below).

What has been tested: everything below runs in the project's testbed, where MAME stands in for
the SE's logic board and QEMU for the Pi (docs/08 item 28 on GitHub: System 7.1's Finder on the
SE's own screen, booted from the SE's SCSI disk). What has NOT been tested: the Pi talking to
a real CPLD and a real SE. This build is how that gets tested. Keep a serial cable on the Pi's
GPIO 14/15 (115200 8N1): the kernel's log is the only window into the first boots.

Which Raspberry Pi
------------------
The classic PiStorm board is laid out for a Pi 3A+. In the SE take a 3A+ or a Zero 2 W: both
fit the board. A 3B or 3B+ works but overhangs it; a Pi 4 does not go on the classic board (the
bench only). The original Pi Zero W (2017) cannot run this at all: its processor is 32-bit only.

  Pi        where                  WiFi                     Bluetooth    wired       USB input        card writer  RAM (Mac)
  3A+       SE (fits) or bench     BCM43455, 2.4+5 GHz      BCM4345C0    none (1)    1 port, hub (2)  yes          512 MB (128)
  Zero 2 W  SE (fits (3)) or bench BCM43436/43436s, 2.4 GHz BCM43430B0   none (1)    OTG adapter (2)  yes          512 MB (128)
  3B        bench; SE overhanging  BCM43438, 2.4 GHz        BCM43430A1   LAN9514     4 ports          yes          1 GB (128)
  3B+       bench; SE overhanging  BCM43455, 2.4+5 GHz      BCM4345C0    LAN7800     4 ports          yes          1 GB (128)
  4B, 400   bench only             BCM43455                 BCM4345C0/C5 Gigabit     not yet          no           2-8 GB (128)
  Zero W    does not work (32-bit only)

  (1) No wired port: the kernel leaves the wired card out of the Mac's slot 9, so the WiFi is the
      Mac's network card. eth=usb in cmdline.txt takes a USB Ethernet adapter instead (a LAN9500,
      LAN7800 or CDC-ECM one, on the port or behind a high-speed hub there).
  (2) One USB port only (the 3A+'s USB-A socket; the Zero 2 W's micro-USB "USB" port, not the one
      marked PWR, through an OTG adapter). A keyboard and a mouse together need a small hub on it,
      or a keyboard-and-mouse receiver (one device, both work). Plugging the hub in or out is seen.
  (3) The Zero 2 W comes without a header: solder a 40-pin male header, or buy the Zero 2 WH.
      Mini-HDMI for the Pi's screen, power on the PWR port.
Memory on a 512 MB Pi: the Mac gets its 128 MB, the kernel its own pools, and a disk image on the
card can be up to about 99 MB (one in the container about 100 MB; a larger one leaves the Mac
less than 128 MB). The log says what it
chose ("[PSMAC] board: ...", "[PSMAC] memory: Mac 128 MiB, ... a disk image on the card can be up
to N MB"); an image that does not fit is reported ("[CARD] MEMORY: ...") and mac.ram=N makes room.

Setting up the SD card (a Pi 3B in an SE)
-----------------------------------------
  1. Format a microSD card as one FAT32 partition (any size from 1 GB).
  2. Put the Raspberry Pi firmware on it, and fetch the WiFi and Bluetooth firmware. The easy
     way: copy get-firmware.sh from this zip to the card's root folder and, from a terminal there
     (macOS or Linux; on Windows use WSL or the manual way below):

        sh get-firmware.sh

     It downloads the Pi's boot files into the card's root (for a Pi 3B, 3B+, 3A+, Zero 2 W and
     Pi 4 alike) and the WiFi and Bluetooth firmware of every board into wifi-firmware/, each from a
     fixed version and checked against its SHA-256, refuses anything too small to be firmware,
     and prints the make-container.py line for step 5. Run it again and it keeps what is already
     right. With your ROM beside it, "sh get-firmware.sh --container MacIIci_368CADFE.rom"
     makes aurora68.cpio as well. Nothing of Apple's is downloaded: the ROM and the system
     software are yours to supply. Then skip step 4.
     The manual way, from a terminal in the card's root folder:

        curl -fL --remote-name-all \
          https://raw.githubusercontent.com/raspberrypi/firmware/master/boot/bootcode.bin \
          https://raw.githubusercontent.com/raspberrypi/firmware/master/boot/start.elf \
          https://raw.githubusercontent.com/raspberrypi/firmware/master/boot/fixup.dat \
          https://raw.githubusercontent.com/raspberrypi/firmware/master/boot/bcm2710-rpi-3-b.dtb \
          https://raw.githubusercontent.com/raspberrypi/firmware/master/boot/bcm2710-rpi-3-b-plus.dtb \
          https://raw.githubusercontent.com/raspberrypi/firmware/master/boot/bcm2710-rpi-zero-2-w.dtb
        mkdir -p overlays
        curl -fL -o overlays/disable-bt.dtbo \
          https://raw.githubusercontent.com/raspberrypi/firmware/master/boot/overlays/disable-bt.dtbo

     (On Windows, curl.exe; the backslashes continue one command.) The .dtb for your board
     (a 3A+ has none of its own: its firmware loads bcm2710-rpi-3-b-plus.dtb, and the kernel
     tells the two apart by the board's revision code) and the disable-bt overlay are needed: the kernel reads the device tree, and the overlay
     puts the PL011 serial port, where the kernel logs, on the header's GPIO 14/15.
  3. Copy everything from this zip to the card's root folder (the Mac folder can stay on your
     PC; its files go to the Macintosh, not the Pi).
  4. (Not needed after get-firmware.sh.) Get Broadcom's firmware for the Pi's WiFi (and
     Bluetooth, for later). In the same folder:

     Pi 3B (BCM43438):
        curl -fL --remote-name-all \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/cypress/cyfmac43430-sdio.bin \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/brcm/brcmfmac43430-sdio.txt \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/cypress/cyfmac43430-sdio.clm_blob \
          https://raw.githubusercontent.com/RPi-Distro/bluez-firmware/master/broadcom/BCM43430A1.hcd

     Pi 3B+, 3A+ (BCM43455):
        curl -fL --remote-name-all \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/cypress/cyfmac43455-sdio-standard.bin \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/cypress/cyfmac43455-sdio.clm_blob \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/brcm/brcmfmac43455-sdio.txt \
          https://raw.githubusercontent.com/RPi-Distro/bluez-firmware/master/broadcom/BCM4345C0.hcd

     (In that repository brcm/brcmfmac43430-sdio.bin and .clm_blob are links to the cypress files;
     the raw download of a link is a 31-byte path, not firmware. The sizes to expect: the .bin
     about 400 KB, the .clm_blob about 5 KB, the .txt about 1 KB, the .hcd about 30 KB.)

     Pi Zero 2 W (BCM43436, or the later BCM43436s: take both sets, the kernel picks by the chip's
     revision, and the 43436s uses the 43430's .clm_blob from the Pi 3B list above):
        curl -fL --remote-name-all \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/brcm/brcmfmac43436-sdio.bin \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/brcm/brcmfmac43436-sdio.txt \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/brcm/brcmfmac43436-sdio.clm_blob \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/brcm/brcmfmac43436s-sdio.bin \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/brcm/brcmfmac43436s-sdio.txt \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/cypress/cyfmac43430-sdio.clm_blob \
          https://raw.githubusercontent.com/RPi-Distro/bluez-firmware/master/broadcom/BCM43430B0.hcd

  5. Make the container, the one file the Pi firmware loads besides the kernel. Put your own
     Macintosh IIci ROM image (version 368CADFE, 512 KB; Apple's ROM is not included) next to
     make-container.py as MacIIci_368CADFE.rom and run (Python 3 needed), for a Pi 3B:

        python3 make-container.py -o aurora68.cpio MacIIci_368CADFE.rom \
          aurora68-512x342.declrom aurora68.declrom \
          cyfmac43430-sdio.bin brcmfmac43430-sdio.txt cyfmac43430-sdio.clm_blob BCM43430A1.hcd

     (for a 3B+/3A+, the cyfmac43455 files and BCM4345C0.hcd instead; for a Zero 2 W the 43436
     ones above). The stock ROM is patched on the way; the
     output says so. The kernel also patches a stock ROM itself when it finds one in the
     container ("stock IIci ROM 368cadfe in the container: patched in memory ... verified" in
     the log), so an unpatched container works too. Copy aurora68.cpio to the card. The two declaration ROMs: the kernel takes
     the one whose name ends in the screen size in use, 512x342 on the SE board.
  6. Check cmdline.txt: one line, "enable_cache debug mac.board=se bt=off mac.console=hdmi".
     mac.board=se tells the kernel it is in a Macintosh SE and not in the testbed's IIci. In a
     Macintosh Plus, 512Ke, 512K or 128K write mac.board=plus, 512ke, 512k or 128k instead (not
     yet tried on a real machine: "The Plus, 512Ke, 512K and 128K", below).
     mac.console=hdmi keeps the kernel's log on the HDMI screen for the whole run, the same text
     as the serial line, so a bench without a serial cable still sees everything; take it out
     to have HDMI show the Macintosh's picture instead (the log then shows until the
     Macintosh's video driver turns the screen on). To join a WiFi
     network at boot add wifi.ssid=NAME wifi.psk=PASSWORD wifi.country=CC, where CC is your
     own country's two-letter code (GB, DE, FR, US, AU ...); "XX" is not a country, and the
     kernel ignores it.
     Memory: the kernel gives the Macintosh what the Pi can spare, up to 128 MB (on every board,
     the 512 MB 3A+ and Zero 2 W included); mac.ram=N fixes it.
  7. The PiStorm: the classic board, with the firmware it came with. Remove the SE's 68000 (or
     use the socket if yours has one), seat the PiStorm with pin 1 where the 68000's pin 1 was
     (the notch end), the Pi on it. A 3A+ or a Zero 2 W fits the board; a full-size Pi 3B or 3B+
     overhangs it: make sure nothing under it touches the logic board.
  8. HDMI to a monitor if you have one (it shows the same 512 by 342 picture as the SE's screen
     in this build), the serial cable to GPIO 14 (TXD) and 15 (RXD), ground to 6. Power the SE.

Disks: what the Mac can use (0.13)
----------------------------------
Every disk is HFS ("Mac OS Standard") as far as the Mac is concerned; System 6 and 7 read nothing else.
  - The SE's own SCSI bus (its internal disk, a BlueSCSI, SCSI2SD, ZuluSCSI): a disk with an Apple
    partition map, a driver partition (Apple's Apple_Driver43 from HD SC Setup, or another formatter's)
    and an HFS volume. It can be the startup disk. On a BlueSCSI the image files are named HDxy_512.hda
    (x the SCSI ID, y the LUN). A bare HFS image with no driver does not mount on SCSI.
  - Disk images on the SD card: files in the card's root ending in .img, .hda, .image, .hfv or .dsk,
    1 MB or more, up to four (or those named by mac.image=). Bare HFS images (hformat, Basilisk II, Mini
    vMac) and Apple-partitioned ones (the first Apple_HFS partition is used) both work. They are read
    into the Pi's memory: a few hundred MB on a 1 GB Pi, about 100 MB on a 512 MB one. What the Mac
    writes is saved back into the file. One holding a System can be the startup disk (mac.boot=).
  - USB sticks: formatted FAT32 or exFAT on a modern Mac or a PC, their files appear as a locked disk,
    Mac files intact (macOS keeps resource forks, type and creator in "._" files beside them); HFS disk
    images in the stick's root mount as disks of their own and can be written to. A stick that is HFS
    itself mounts as it is. Up to 2 GB and 32,000 files per view; writing to a FAT/exFAT stick's own
    files is not done yet. Eject: Put Away, then wait for "safe to unplug" in Aurora68 Log.
  - A folder "Mac Exchange" in the card's root: its files as a locked disk, put there from any computer.
  - A BlueSCSI or other disk on the SE's own SCSI bus: found again in 0.13 (Apple's 250 ms selection
    timeout). A disk image made from an Aurora68 card image may carry Iomega's Zip driver and the Iomega
    Driver extension: the Mac then says "This is not a Macintosh disk" with Iomega's icon. Move "Iomega
    Driver" out of the Extensions folder (start with Shift held); tools/mac/swap_driver.py (in the
    repository) gives an image Apple's SCSI driver from one of your own disks.
  - The SE's floppy drive: 0.12 selects the internal drive (it did not before); not yet verified on a
    real SE.
Tested Systems: 7.1 (also 7.1.2) and 6.0.8. More than 8 MB needs 32-bit addressing (System 7's Memory
control panel); System 6 sees 8 MB at most.
Does not work: HFS Plus or APFS disks, Disk Copy 4.2 floppy images (an 84-byte header: convert them to
a raw image), .dmg, .sit, .toast and CD-ROM images.
The startup disk: a floppy with a System first; then with mac.boot=auto (the default) the SCSI disk the
Startup Disk control panel names, then a disk image on the card, then the other SCSI disks.
mac.boot=image puts the card's image first.

Two screens: the SE's and HDMI
------------------------------
Once the SE's own screen shows the Finder, HDMI can be a second screen beside it (any size up to
2560 x 1440, up to millions of colours) instead of the log or a copy of the SE's picture:
  1. In the container, aurora68-se.declrom instead of aurora68-512x342.declrom. It serves every HDMI
     size: the kernel fits its screen to the HDMI mode of config.txt at every start, so the container
     need not be rebuilt for another monitor (aurora68-se-WxH.declrom, one per size, still work). A
     .declrom file in the card's root is taken before the container's: copy a new one there to
     update the Mac's drivers, and remove old ones.
  2. config.txt: hdmi_group=2 and the hdmi_mode of that size (16 = 1024 x 768, 9 = 800 x 600,
     82 = 1920 x 1080, 69 = 1920 x 1200); keep gpu_mem=64. For 2560 x 1440 (30 Hz, the most a Pi 3
     drives at that size): hdmi_mode=87, hdmi_cvt=2560 1440 30 3 0 0 1, max_framebuffer_width=2560
     and max_framebuffer_height=1440, with aurora68-se-2560x1440.declrom and mac.screen=2560x1440.
  3. cmdline.txt: take out mac.console=hdmi; the size is config.txt's (mac.screen=WxH only to
     differ from it), e.g. "enable_cache debug mac.board=se bt=off".
  4. Copy Aurora68 Screen Setup (Mac/Aurora68/Extensions (to install)/, or the Aurora68 disk
     image) onto the System Folder. At the next
     start it arranges the two screens (the SE's main, HDMI to its right) and restarts the Mac once.
  5. Millions of colours need 32-bit addressing: Memory control panel, On, restart, then Millions
     for monitor 2 in Monitors.
mac.hdmi=mirror shows the SE's picture on HDMI again, mac.hdmi=log (or mac.console=hdmi) the log.

Choosing the HDMI resolution on the Mac: Aurora68 Display
---------------------------------------------------------
Aurora68 Display (Mac/Aurora68/Display/) shows what the HDMI monitor says about itself (name, maker, serial number,
size, sound) and every resolution it lists, each marked usable, too fast for a Pi 3 (with a slower
alternative when one fits, such as 2560 x 1440 at 30 Hz) or the wrong shape, with a suggestion; and it
sets the resolution and turns the picture (0, 90, 180, 270 degrees).
  1. Once: config.txt ends with the line "include aurora68-display.txt" (this release's config.txt has
     it), and aurora68-display.txt is on the card beside it (this release's holds comments only).
     Keep the include line last: an hdmi_ line after it would win.
  2. Aurora68 Screen Setup in the System Folder (it asks "Keep this resolution?" after a change).
  3. In Aurora68 Display choose a resolution and/or a rotation, then Restart to Apply. A new
     resolution restarts the Pi and the Mac; on the SE's screen Aurora68 Screen Setup then asks "Keep this resolution?": Keep,
     or within 15 seconds the previous one comes back by itself (the Pi restarts once more). A rotation
     restarts the Mac only.
The kernel writes aurora68-display.txt and keeps the one before as aurora68-display.bak; config.txt is
never written. The log's [PSMAC:EDID] lines list the monitor's modes; send them if something is wrong.

Sound on the HDMI monitor
-------------------------
The Mac's sound plays on the HDMI monitor's loudspeakers in stereo (and on the SE's speaker as before):
  1. config.txt: hdmi_drive=2 (in this release's config.txt): HDMI with sound rather than DVI.
  2. Copy Aurora68 Sound (Mac/Aurora68/Extensions (to install)/, or the disk image) into the System Folder. It
     needs Sound Manager 3.0 or later (the "Sound Manager" extension on System 7.1): the Sound Manager
     then plays into a 16-bit stereo sound card that the Pi plays. Without it the sound still reaches
     HDMI, from the IIci's 8-bit sound chip.
  3. Nothing in cmdline.txt: mac.audio=hdmi is the default. mac.audio=jack uses a Pi 3's headphone
     socket instead, mac.audio=off neither; mac.audiotest=card plays 441 Hz on the left and 882 Hz on
     the right for three seconds at start, to check the channels.
The log says what happened: "[AUDIO] HDMI: 48000 Hz stereo ..." and "[MAC] A68 Sound: ...". If it says
"the transmitter sends no packets ... DVI", hdmi_drive=2 is missing or the monitor has no sound.

QuickTime movies on the video decoder card
-------------------------------------------
The Pi has a video decoder card for the Mac (slot $C, "Aurora68 Video Decoder" in Aurora68
Slots): it decodes QuickTime's Cinepak, Apple Video, Animation and Graphics movies on a Pi core
and draws them into the Mac's screen, the SE's own included. To use it:
  1. QuickTime 2.0 or later on the Mac (2.5 is the last for 68k Macs; it is Apple's, not ours).
  2. Copy "Aurora68 Video Decoder" from Mac/Aurora68/Extensions (to install) onto the closed
     System Folder (System 7 puts it into Extensions) and restart.
  3. Open a movie in MoviePlayer, or in any program that plays QuickTime movies.
The Pi's log says "A68 Video Decoder: Cinepak 320x240: decoded by the card into a 1-bit pixel map"
when a movie starts on the card, and when it is closed how many pictures came and how long each
took. mac.vdecode=off in cmdline.txt switches the card off for comparison: QuickTime's own
decompressors then play the movie (the log says so). Please send the two lines from each, with
and without, for a Cinepak movie on the SE's screen and, if you have one, on HDMI at 256
colours and at thousands: they are the measurements the testbed cannot make.

MPEG-1 films (.mpg with MP2 sound) play on the same card in Aurora68 Video (Mac/Aurora68/Aurora68
Video): File > Open..., or double-click a file of type MPEG. Space plays and pauses, a click in the
bar seeks, Movie > Double Size doubles the picture. Its Card menu switches QuickTime decoding on the
card on and off without restarting. To make such a film on another computer: ffmpeg -i in.mp4
-vf scale=320:240 -c:v mpeg1video -b:v 800k -c:a mp2 -b:a 128k -ar 44100 -f mpeg out.mpg

The same films also open in MoviePlayer (and any QuickTime program) with the Aurora68 Video
Decoder extension installed: File > Open..., choose the film, click "Convert" (it opens the film
where it is; nothing is copied). The first opening takes a few seconds more while the card decodes
the sound into the Preferences folder ("Aurora68 Video Sounds"; delete it to make room). What to
try on the SE: open a film, play it, click in the middle of the slider (the picture there should
be right at once), play it again with Movie > Play All Frames, and note in Aurora68 Log the lines
"A68 Video Decoder: MPEG-1 ..." and how smoothly it played with its sound.

Music videos in Aurora68 Play (1.6): with the video decoder card above, a video in the music server's
library (a "Video:" row after an album's songs, or one sent from the server's web page) plays in a window
of its own on the SE's screen, or in colour on HDMI if Aurora68 Play's window is there. Click in the
picture or press the space bar to pause; click the progress line in Aurora68 Play's window to jump; the
close box hides the picture and the sound goes on (Controls > Show Video brings it back). The log says
"A68 Play: video: played to the end ..." with the numbers the testbed cannot give: please send those lines
(the network's rate, "under 8 KB in hand for ... ms", the pictures shown and not drawn) from the SE.

Aurora68 Play 1.7 finds the music server by itself: at its first start, or when the server it knew does
not answer, it asks the network and connects to the server that answers. With two servers it asks you to
choose one in Library > Servers (also Search Again, and Connect to Server... for an address). A song with
a music video has a film mark; Library > Play Video (Command-M) plays it; Controls > Play Videos Instead
of Songs plays each song's video in its place (with the video decoder card); Library > Videos lists every
video by artist, Library > Up Next the queue; Play Next and Add to Queue, Repeat One; the video window's
zoom box, or Command-1, 2 and 3, make the picture Normal Size, Double Size or Fill Screen. Please say
whether the server was found on your network, and which line of Aurora68 Log says so ("A68 Play:
library: found the music server ...").

Aurora68 Play 1.8: drag the video window's size box (in the strip under the picture) to make the picture
any size of its own shape; the zoom box toggles Fill Screen and that size, which the next video keeps.
The player and Library windows remember their places for each arrangement of screens (the SE's alone, or
with HDMI). Titles say "Artist - Title". The video goes on playing when another program is in front, or
behind another window, wherever its window shows (this needs the kernel8.img of the same release: the
card reads the window's region itself). Connect By is IPv6 First by default: the server's IPv6 address is
tried first and its IPv4 address after five seconds without an answer; IPv4 Only is new. Please send the
lines of Aurora68 Log starting "A68 Play: library: the server's addresses", "it names IPv4" and "the server
answers at", and, if the Play locks up again, the last "A68 Play:" lines and the kernel's log (the serial console, or Setup and
Recovery's log after a restart): a line "the event loop was away ..." says what the stream was doing.

MP3 files: copy the folder Aurora68 Play (Mac/Aurora68/) onto the Mac and the MP3s anywhere on its
disks (a USB stick or the Lagoon share will do; files from a PC need no Mac type). Open one with File >
Open..., or drop it on Aurora68 Play's icon; the space bar plays and pauses. Files given the type MPG3
and the creator PIPY (aurora68-layout.py does it for the Music folder) open with a double-click. The Pi
decodes the MP3 and plays it with the Mac's own sound; the log says "[AUDIO] stream: MPEG-1 layer III,
44100 Hz stereo, ..." and "[MAC] A68 Play: ...". Every Aurora68 program's lines in the log start
"[MAC] A68 " and its short name: A68 Play, A68 Display, A68 Slots, A68 Sound, A68 Screen Setup...

The Plus, 512Ke, 512K and 128K (in the next release; testbed only so far)
-------------------------------------------------------------------------
The kernel has boards for the other compact Macs. All four reach System 7.1's Finder in the
project's testbed (MAME's Plus, 512Ke and 128K/512K logic boards with the Pi's bridge); none has
been run on a real machine. Set the card up as for the SE, with one difference in cmdline.txt:
  Macintosh Plus     mac.board=plus      SCSI as on the SE: its disk or a BlueSCSI
  Macintosh 512Ke    mac.board=512ke     no SCSI: the System from a disk image in the card's root
  Macintosh 512K     mac.board=512k      no SCSI, and the 20-byte clock chip (below)
  Macintosh 128K     mac.board=128k      the same as the 512K
  - The 68000 on these logic boards is usually soldered in. The PiStorm needs a 64-pin socket in
    its place (or a clip-on adapter); fitting one is work on the board for someone who has done
    it before. Look at yours before you start.
  - The keyboard and mouse are the machine's own (not ADB on any of these): the kernel presents
    them to the IIci ROM as ADB devices. USB and Bluetooth keyboards and mice work as on the SE.
  - Memory is the Pi's, as on the SE. With System 7.1 give the Mac 32 MB or more (the default
    is up to 128 MB): at 8 MB in 24-bit mode QuickTime crashes at start-up.
  - Parameter RAM: the 128K's and 512K's clock chip holds 20 bytes and not the rest the IIci ROM
    wants, so all of it is kept in pram.bin on the card. A first start from blank or untrusted
    parameter RAM (a Plus at its first start with Aurora68) still starts from the card's image.
  - SANE: exact SANE comes from the machine's own ROM where it holds PACK 4 and 5 (the log says
    "[PSMAC] SANE: ..."). The 128K's and 512K's ROM has none: there the IIci ROM's SANE stays,
    unless mac.serom=FILE names an SE ROM image you have put on the card yourself.
  - The floppy drives of these machines have not been tried yet.
  - mac.fpu=none gives the Mac no FPU, as these machines really have none: programs then use
    their own non-FPU code, exact but slower.
  - What to send back: the serial log (or the HDMI log, mac.console=hdmi) of the first boot, and
    a photo of the screen, through an issue on GitHub (issue #21 is the Plus's).

If your Mac misbehaves: the bus check (in the next release)
------------------------------------------------------------
A screen with stray dots, a mouse that moves by itself, phantom keys, a Mac that will not start:
before anything else, let the kernel measure the bus between the Pi and the logic board. It takes
a few seconds and gives everyone the same numbers to compare.
  1. Add to the one line of cmdline.txt, beside your mac.board=:   mac.buscheck=1
  2. Power on with the mouse still and nothing pressed. The Mac does not start in this boot: after
     a few seconds of a grey striped screen, the Mac's own screen (and HDMI, if connected) shows
     one page headed AURORA68 BUS CHECK.
  3. Photograph the whole page, sharp enough to read the numbers. The last lines under SUMMARY say
     in plain words what was found ("all clean", "D11 always reads 0: a stuck data line", "reads of
     RAM fail ... mostly at random: a timing problem", ...).
  4. Power off. The same text is in buscheck.txt in the card's root (with more detail): send it and
     the photo with your issue on GitHub. Take mac.buscheck=1 out of cmdline.txt to use the Mac.
  - Do it three or more times from cold (power off for ten seconds between): the Plus-era boards
    can come up in a different phase each time, and the "phase read D0" line says which.
  - mac.buscheck=loop measures again and again until you power off: useful while you press on the
    PiStorm or warm the board, to see whether the numbers move.
  - The page's CPLD line names the PiStorm's firmware (its JTAG usercode): say it in your issue.

The bus check from a phone, and one file to send (Setup and Recovery's Diagnostics tab)
--------------------------------------------------------------------------------------
No need to edit cmdline.txt for it. Start Setup and Recovery (hold the programmer's interrupt switch,
the one nearer the back, while you switch on; or three starts that did not reach the Finder), open the
address the Mac's screen shows on a phone or laptop on the same network, give the PIN, then the
Diagnostics tab:
  1. Run now > Bus check > Run. The page shows each test as it starts, then the report and its
     verdict; the Mac's own screen and HDMI show the same page as with mac.buscheck=1. Photograph the
     Mac's screen as above, then "Give the screens back to Setup and Recovery". buscheck.txt is
     written to the card. Run it three times from cold if you can (power off ten seconds between).
  2. Run now > Card read test > Run: the card's speed and any read error (cardcheck.txt).
  3. Report bundle > Download the bundle: aurora68-report.txt, one text file with the board, the
     kernel's build, the CPLD usercode, the memory, the options in effect, every report and both
     logs. WiFi passwords, tokens and the PIN are already replaced by "(hidden)". Attach it to your
     issue on GitHub with the photo.
  - To catch a fault that only shows while the Mac runs: Run on the next start, tick "mac.logsave"
    (the log saved to the card every few seconds) and whatever traces the issue asks for, then "Arm
    and restart normally". Those options are used for that one start only. Afterwards start Setup
    and Recovery again and download the bundle: the saved log is in it.

A Pi on the bench, no SE yet
----------------------------
That is a useful first test. Power the Pi from USB with HDMI connected. The firmware's rainbow
square for a moment, Emu68's splash, then the log scrolling on HDMI (white on black, wrapping
to the top when it reaches the bottom). Expect "bridge=gpio", "protocol up" with whatever the
floating pins read, "board layer up", then either bus cycles that "complete" with junk or "the
CPLD did not finish a bus cycle ... is the Pi in a Macintosh?" and "TRANSPORT DEAD" in the
heartbeats: both are right for a Pi with nothing behind it. The "[WIFI]" lines are the ones that
matter on the bench: the chip id (a9a6 is a Pi 3B's 43430), "Cortex-M3 + SOCRAM", the firmware
loaded and running, a scan if wifi.ssid= is set. A photograph of the screen at a heartbeat is a
log. Nothing at all on HDMI, not even the rainbow square: the firmware did not start; look at
the green ACT LED (a repeating pattern of flashes is the firmware's error code: 4 means
start.elf not found, 7 kernel not found) and at the card (ejected properly, FAT32, files in the
root).

Booting System 7 on the bench, no SE at all (new in 0.4)
--------------------------------------------------------
The kernel can stand in for the whole logic board: with "mac.board=solo" it answers the VIA,
the clock chip, the ADB transceiver (no keyboard or mouse yet), the SCC, the floppy controller
(no drive) and a SCSI controller with a disk for each disk image in the container. So:
  1. Get a Macintosh hard disk image that boots System 7 on a IIci: an Apple-partitioned image
     with a driver partition and an HFS volume (what HD SC Setup or a Mac emulator makes). The
     file name must end in .img, .hda, .image or .hfv. Up to a couple of hundred megabytes on a
     1 GB Pi, about 100 MB on a 512 MB 3A+ or Zero 2 W with the Mac at 128 MB (it is loaded into
     memory with the rest of the container; a larger one leaves the Mac less).
  2. Add it to the container: python3 make-container.py -o aurora68.cpio MacIIci_368CADFE.rom
     aurora68.declrom aurora68-512x342.declrom MyMac.img  (plus the WiFi files if you want the
     WiFi; the order does not matter). Copy aurora68.cpio to the card.
     For the network, use aurora68-wifi.declrom instead of aurora68.declrom: MacTCP takes the
     first network card it finds, and that file has only the WiFi one (a Pi 3 has no wired
     Ethernet). config.txt must say "initramfs aurora68.cpio 0x10000000" (0.4's does; with
     "followkernel" a large container lands in the kernel's early tables and the Mac shows the
     blinking question mark).
  3. cmdline.txt, one line: "enable_cache debug mac.board=solo bt=off" (no mac.console=hdmi:
     the log shows until the Mac's video driver takes the screen, then the Mac does). Add the
     wifi.ssid= / wifi.psk= / wifi.country= words if you like, and mac.screen=WxH for a bigger
     screen with the matching declaration ROM in the container.
     A Pi 3 at a bigger screen with the WiFi: the kernel now drives the Pi 3B's and 3B+'s wired
     port too, so the Mac gets both cards ("One card for a Pi 3 and a Pi 4" below); MacTCP takes
     the first, the wired one. On a Pi with no wired port (3A+, Zero 2 W) or with eth=off the
     kernel takes the wired card out of the declaration ROM by itself, so the ordinary
     declaration ROM of the screen's size will do; the WiFi-only ones (aurora68-wifi-WxH.declrom)
     say the same thing in the file. For a
     1080p monitor (hdmi_group=2, hdmi_mode=82 in config.txt, mac.screen=1920x1080 in
     cmdline.txt):

        python3 make-container.py -o aurora68.cpio MacIIci_368CADFE.rom \
          aurora68-wifi-1920x1080.declrom MyMac.img \
          cyfmac43430-sdio.bin brcmfmac43430-sdio.txt cyfmac43430-sdio.clm_blob BCM43430A1.hcd

     Put only one declaration ROM of each size in the container: with both
     aurora68-1920x1080.declrom and aurora68-wifi-1920x1080.declrom the kernel takes whichever
     comes last. The log says "the wired Ethernet card ($81) left out" when it hides the card.
     For a 1920 by 1200 monitor in millions of colours: in config.txt hdmi_group=2 and
     hdmi_mode=69; in cmdline.txt mac.screen=1920x1200; aurora68-1920x1200.declrom (on a Pi 3,
     aurora68-wifi-1920x1200.declrom) in the container in place of aurora68.declrom. On the Mac choose Millions in Monitors (32-bit
     addressing must be on; the solo board's parameter RAM has it on). The choice is kept in
     pram.bin on the card (below); Aurora68 Depth 8 (in Mac/Aurora68/Display/), renamed
     "Aurora68 Depth 32" in the System Folder's Startup Items, still sets it at every start if you prefer.
  4. Boot. The ROM's memory test takes a few seconds, the happy Mac appears, then "Welcome to
     Macintosh" and the Finder, about a minute on a Pi 3.
  5. Mouse and keyboard, over Bluetooth (new in 0.5). The kernel starts the Pi's Bluetooth unless
     cmdline.txt says bt=off; with bt.pair=1 (in the shipped cmdline.txt) it pairs with the first
     keyboard or mouse it finds in pairing mode and looks again every 20 seconds, so put the
     device in pairing mode any time after the boot. A keyboard shows a passkey in the log
     (mac.console=hdmi to see it): type it on the keyboard and press Return. Once paired, the
     kernel saves it in pairings.txt on the card and the device reconnects at every boot
     without pairing again. Classic Bluetooth and Bluetooth LE mice and keyboards both work.
     Or over USB (new in 0.7): plug a USB keyboard and mouse into the Pi 3's USB ports, before
     or after the boot (a 3A+ or Zero 2 W has one port: a small hub on it for both, or a
     keyboard-and-mouse receiver). The Pi uses the first keyboard and the first mouse it finds. If they do
     not work, add usb=pio to cmdline.txt and send the [USB] lines of the log.
What the Mac writes to the image is written back into aurora68.cpio on the card a second or two
after the Mac stops writing (new in 0.5), so the next boot starts where the last one ended. Keep a
copy of aurora68.cpio somewhere else: a power cut in the middle of a write can damage the image,
as it would a real disk. Bluetooth pairings are kept in pairings.txt on the card, which the
kernel creates; the bt.dev= words in cmdline.txt still work and are read first. mac.card=ro or
mac.card=off in cmdline.txt stop the writing. Parameter RAM (new in the next release) is kept
in pram.bin on the card, as a real Mac keeps it in a chip with a battery: AppleTalk active in the
Chooser, the Network control panel's choice (Lagoon EtherTalk), Monitors' depth, the startup disk,
the sound. The kernel writes it a second after the Mac changes it, once the Finder is up, and reads
it before the Mac does at the next power-on; the clock goes on from where the last save left it.
mac.appletalk=1 and mac.xpram= still apply on top of it. Delete pram.bin to start from the
defaults. With
mac.board=se (the SE board) the same image appears as a PiDisk volume instead.

A Pi Zero W (the original, 2017) cannot run this: its processor is 32-bit only. The Zero 2 W can
("Which Raspberry Pi", at the top).

Booting fast (new in the next release)
--------------------------------------
In the SE the Pi is the processor: nothing happens on the Mac until the Pi's firmware has read its
files from the card, the kernel has set up, and the 68k starts. The firmware reads EVERYTHING in
the container before the kernel starts, at 10 to 20 MB a second on a Pi 3, so a container with a
100 MB disk image in it costs five to ten seconds of a dark SE. So:
  - The container holds only the ROM, the declaration ROM and the WiFi/Bluetooth firmware (about
    1 MB). For the SE:
        python3 make-container.py -o aurora68.cpio MacIIci_368CADFE.rom aurora68-512x342.declrom \
          cyfmac43430-sdio.bin brcmfmac43430-sdio.txt cyfmac43430-sdio.clm_blob BCM43430A1.hcd
  - A disk image goes on the card as a file of its own, beside aurora68.cpio, with a name ending
    in .hda, .img, .image, .hfv or .dsk (MyMac.hda; kernel8.img is never taken), or named in
    cmdline.txt with mac.image=NAME. The kernel finds it a moment after the 68k has started and
    reads it in the background while the Mac boots. In the SE it is the PiDisk volume, and the
    startup disk as well when no SCSI disk with a System answers (an SE with nothing attached
    starts from it); on the bench (mac.board=solo) it is the startup disk, SCSI ID 0, and what the
    Mac asks for is read first. mac.boot=image in cmdline.txt makes the image the SE's startup disk
    even with a SCSI disk attached, mac.boot=scsi leaves the choice to the Startup Disk control
    panel. The image must be a startup disk (a System Folder the Mac has started from). What the
    Mac writes goes back into the same file. An image inside the container still works as before,
    and wins if there is one.
  - config.txt: boot_delay=0 (in this release's file). kernel8.img is gzip-compressed (1 MB
    instead of 5); the firmware inflates it itself. Optional: disable_splash=1 (a little faster,
    but the rainbow square is the sign that the firmware found its files) and, in the SE with HDMI
    at 640 x 480 or none, gpu_mem=16 with start_cd.elf and fixup_cd.dat copied from the firmware
    repository (smaller firmware; without those two files the Pi does not start).
  - cmdline.txt for the SE: "enable_cache mac.board=se" plus the wifi.* and bt.* words you use.
    mac.console=hdmi is fine: the log no longer holds the boot up.
    Nor does a serial port that does not send: on a Pi 3 with Bluetooth on the PL011 the kernel
    used to wait for it at every character, 15 seconds of the rainbow screen before the 68k.
  - The bench: the same container with the declaration ROM for your screen, the disk image
    on the card, "enable_cache mac.board=solo mac.screen=WxH ..." in cmdline.txt.
The kernel's log says how long each step took: "[BOOT] t=N.NNNs what", t counted from power-on.
The first line, "kernel entry", is the firmware's part. Please send those lines from your Pi.
The ROM's own start is shorter too: the IIci ROM's memory test (the Pi's memory cannot fail as
SIMMs do), its silent startup chime and its quarter-second wait at every empty SCSI ID are cut
short by the ROM patch the kernel and make-container.py apply.

One card for a Pi 3 and a Pi 4 (new in the next release)
--------------------------------------------------------
The same SD card boots a Pi 3B, a 3B+, a 3A+, a Zero 2 W and a Pi 4 (or 400): one kernel8.img picks its drivers by
board when it starts. Each board gets both its network cards on the Mac, the wired port and the
WiFi, side by side on the one slot-9 card:
    Pi 3B       wired: the LAN9514 on the Pi's USB    WiFi: BCM43438 (the *43430* files)
    Pi 3B+      wired: the LAN7800 on the Pi's USB    WiFi: BCM43455
    Pi 4, 400   wired: the Pi 4's own Gigabit (GENET) WiFi: BCM43455
    3A+, Zero 2 W   no wired port: the WiFi is the only card
What the card needs (get-firmware.sh fetches all of it): bootcode.bin, start.elf and fixup.dat
(the Pi 3's firmware), start4.elf and fixup4.dat (the Pi 4's), the device trees
bcm2710-rpi-3-b.dtb, bcm2710-rpi-3-b-plus.dtb (also the 3A+'s), bcm2710-rpi-zero-2-w.dtb,
bcm2711-rpi-4-b.dtb and bcm2711-rpi-400.dtb, and config.txt with its [pi3] and [pi4] sections (this release's works for
both). The container holds every board's WiFi and Bluetooth firmware; the kernel takes the WiFi
set by the chip's id and the Bluetooth one by the board:

        python3 make-container.py -o aurora68.cpio MacIIci_368CADFE.rom aurora68-1920x1200.declrom \
          wifi-firmware/cyfmac43430-sdio.bin wifi-firmware/brcmfmac43430-sdio.txt \
          wifi-firmware/cyfmac43430-sdio.clm_blob wifi-firmware/BCM43430A1.hcd \
          wifi-firmware/brcmfmac43436-sdio.bin wifi-firmware/brcmfmac43436-sdio.txt \
          wifi-firmware/brcmfmac43436-sdio.clm_blob wifi-firmware/BCM43430B0.hcd \
          wifi-firmware/brcmfmac43436s-sdio.bin wifi-firmware/brcmfmac43436s-sdio.txt \
          wifi-firmware/cyfmac43455-sdio-standard.bin wifi-firmware/brcmfmac43455-sdio.txt \
          wifi-firmware/cyfmac43455-sdio.clm_blob wifi-firmware/BCM4345C0.hcd wifi-firmware/BCM4345C5.hcd

(the declaration ROM of your screen size: one with both network cards, not a -wifi- one). On the
Mac, Riptide uses both cards, en0 the wired one and en1 the WiFi, with DHCP on each and the
default route through the wired one while its cable is in (Riptide's own read-me: "Several
cards"). MacTCP can use one card only, the first: the wired one where there is one. In the
Network control panel Lagoon EtherTalk shows one icon per card, "Lagoon (9)" and "Lagoon Wi-Fi (9)".
Notes:
  - Bluetooth pairings belong to the Pi's Bluetooth chip as much as to the keyboard: one paired
    on the Pi 3 must be paired again on the Pi 4. pairings.txt keeps one key per device, so after
    moving the card back the Pi 3 may need the device paired once more too.
  - The card writer (pairings.txt, and the Mac's changes written back into the disk image on the
    card) works on a Pi 3 only so far: on a Pi 4 the kernel says "the Pi 4's card controller is not
    supported yet: nothing saved" and writes nothing. The image keeps the Pi 3's last state.
  - A Pi 4 does not fit the classic PiStorm board in the SE: a Pi 4 means the bench (mac.board=solo)
    or a different adapter.
  - The wired port on a Pi 3B or 3B+ has only been tested in the project's emulator (with a
    stand-in USB network device); the first real test is yours. The log lines to look for are
    "[ETH] LAN9514 found at USB address 2", "[ETH] MAC ...", "[ETH] link up, 100 Mbit/s full
    duplex", and every 15 seconds "[ETH]   LAN9514: running, link 100 full, rx ... tx ...".
    If the chip is not found the Mac's wired card refuses to open and the WiFi carries on;
    eth=off in cmdline.txt hides the wired card altogether.

Aurora68 Setup and Recovery: when the Mac will not start (new in the next release)
------------------------------------------------------------------------
Inside the SE the Pi's card cannot be reached without opening the Mac. A recovery start is the way
around that: the 68k is not started, no Mac code runs, and the Pi offers its own SD card on the
network. The SE's screen (and HDMI) then says "Aurora68 Setup and Recovery", why, the address to open, and a
four-digit PIN.

Getting in, any of these:
  - The Mac did not reach the Finder in three starts in a row: the fourth start is a recovery start
    by itself. (The count is in boot.txt on the card. Switching the Mac off before the Finder counts
    as a failed start too; a Restart from the Finder does not. mac.bootcount=off switches it off.)
  - Hold the programmer's interrupt switch (the rear button of the two on the SE's left side) while
    you switch the Mac on, and keep holding it for a few seconds.
  - Hold Esc on a USB keyboard on the Pi during the first seconds: the Pi restarts into recovery.
  - Put a file named recovery.txt on the card (it is removed when recovery starts), or, from a
    running Mac with the remote control on: python3 aurora68.py restart recovery
  - mac.recovery=1 in cmdline.txt.

Connecting:
  - With the Pi's wired port or a USB Ethernet adapter (eth=usb) on your network: open the address
    the screen shows, or http://aurora68.local/ . A laptop on a direct cable works too: the Pi takes
    an address of its own after about ten seconds, and http://aurora68.local/ finds it.
  - On WiFi, with the wifi.ssid= / wifi.psk= / wifi.country= options already in cmdline.txt.
  - No network at all, or the WiFi settings wrong: plug a USB keyboard into the Pi and press Return.
    A menu on the screen scans for networks, takes the password and country (your own two letters,
    not XX), sets mac.fpu, mac.boot and mac.console, saves them into cmdline.txt (the line before is
    kept in cmdline.bak) and restarts. On a Plus or 512K the Mac's own keyboard works; on the SE it
    does not (the Mac's ROM reads the SE's keyboard, and it is not running).
  - No network at all and only a phone: the Pi's own WiFi network (the access point, new on 23
    November 2026). With the recovery screen up, hold the programmer's interrupt button (the rear
    one) for two seconds. If you are still holding it from switching on, let go first, then press
    and hold again; the screen says "Keep holding the interrupt button" while you do. The screen
    then shows:
        On a phone or laptop, join the WiFi network
        Aurora68-4946                    (yours ends in four characters of your Pi's own)
        with the password (WPA2)
        k7m3qp9xtr                       (a new one at every start)
        then open  http://192.168.4.1/  and give the PIN
        PIN 1234
    Join that network on the phone. The phone usually offers the page by itself ("Sign in to
    network"); if not, open http://192.168.4.1/ in its browser. On the page's WiFi tab type your home
    network's name, password and country and choose "Save and restart to join this network". The
    Pi restarts and joins it; the access point is gone.
    To leave the access point without saving: "Restart normally" on the page, or press the
    programmer's reset button (the front one): the Pi restarts. The access point is never kept.
    If the screen says "no password: this WiFi firmware cannot do WPA2 as an access point", the
    network is open; the PIN still guards the page. If it says "the WiFi chip refused AP mode: ...",
    please send that line and the log (Log tab, or aurora68.log on the card): the access point has
    not been tried on a real Pi yet. A USB keyboard's menu has "Start an access point" too.

The page (a phone is fine) asks for the PIN on the screen once. Then:
  - Files: every file in the card's root, with Get, Rename and Delete; Upload for any file of any
    size (a disk image, a declaration ROM, a kernel). Every upload is read back from the card and
    compared. kernel8.img is never deleted.
  - A new kernel8.img is checked before it is used (its gzip data and checksum, the ARM64 header,
    that it is an Aurora68 kernel) and only then replaces the old one, which stays as kernel8.old.
    "Roll back the kernel" puts kernel8.old back; when the Finder was not reached three times and a
    kernel8.old is there, the page offers it at the top.
  - WiFi: Scan, choose a network, type the password and country, "Test join now" (it says whether
    it joined), then "Save to cmdline.txt".
  - Options: the usual cmdline.txt options as a form; the new line is shown before it is saved, and
    every other word of the line stays as it was. cmdline.txt and config.txt can also be edited as
    text; the old one is kept as cmdline.bak / config.bak. cmdline.txt must stay one line.
  - Log: the last start's aurora68.log (on the SE it is saved every 30 seconds) and this recovery
    start's log.
  - Display: the HDMI monitor, for one that shows nothing or a Mac that does not start. What the
    monitor says about itself (maker, model, size, its own resolution), the resolution in force,
    a suggestion with its reason ("Use the suggestion"), and every resolution the monitor lists,
    each marked usable, too fast for the Pi 3 with a slower one that fits (2560 x 1440 at 30 Hz),
    or too fast (dimmed). "Automatic" lets the Pi's firmware choose the monitor's own. The picture
    can be turned (0, 90, 180, 270 degrees). The choice goes into aurora68-display.txt (the old one
    is kept as aurora68-display.bak); if config.txt lacks its last line "include
    aurora68-display.txt", the page offers to add it (config.bak keeps the old config.txt). Then
    "Restart normally": at that start Aurora68 Screen Setup asks on the SE's own screen whether to
    keep the new resolution, and puts the old one back if nobody answers. With no monitor
    connected the usual resolutions are offered instead.
  - "Restart normally" (it also takes mac.recovery=1 and recovery.ap out of cmdline.txt) and "Restart
    into recovery".
From a computer: python3 aurora68.py recovery --url http://aurora68.local --pin 1234 ls
(also put FILE, get NAME, rm NAME, mv A B, cmdline, opt, wifi, log, rollback, reboot normal,
display, display use 2560x1440@30 --add-include, display use auto).

Safety: every request needs the PIN, which is new at every recovery start; after ten wrong ones the
PIN changes and the Pi does not answer for a minute. Only the local network is answered. The WiFi
password is never shown back (it reads "set"), and the PIN is never written to the log.

What it cannot do: a kernel8.img that stops before it reads the card cannot get you into recovery,
and the Pi 3's firmware has no fallback kernel of its own that we know of. Keep a known good
kernel8.img, and consider a microSD extension cable led out of the case. This has been tested in
the project's emulators only; your first real test of it is welcome.

What to expect, and what the log says
-------------------------------------
On the serial line, within a second: Emu68's banner, then "[PSMAC] options: ... bridge=gpio
(classic PiStorm)", "[PSMAC:GPIO] classic PiStorm protocol up ... RESET free", "[PSMAC:SE]
board layer up". Then the ROM runs: "[PSMAC] heartbeat" lines every five seconds with the bus
cycle counts. On the SE's screen: nothing for the first seconds (the memory test), the
startup chime from the SE's speaker is NOT expected yet (the ASC the ROM plays through is a
stand-in), then the grey desktop with the blinking disk if no startup disk is found, or the
"Welcome to Macintosh" from your SCSI disk.

If the log says "the CPLD did not finish a bus cycle ... is the Pi in a Macintosh?" the Pi is
not talking to the CPLD: seating, orientation, or the board's firmware. If the SE's screen
stays blank while the heartbeats show bus traffic, send the log: that is the SE's real timing
meeting a translation that has only met MAME's. Every finding goes into docs/08 on GitHub.

On the Macintosh
----------------
The drivers need no installation: they are in the declaration ROM. From Mac/Aurora68/Extensions (to
install)/, put the extensions you want into the System Folder (System 6) or drop them on the closed
System Folder (System 7 puts them into Extensions); copy the Aurora68 folder anywhere.
Aurora68-Utilities.img is an HFS disk image with all of them in the same folders. With hfsutils on a
PC, tools/mac/aurora68-layout.py (in the source) installs the whole set onto a Mac disk image.
