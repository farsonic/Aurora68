Aurora68 0.4 - a Macintosh SE build that also boots System 7 on a Pi alone
==================================================

What this is
------------
Aurora68 puts a Raspberry Pi in a Macintosh SE's 68000 socket on a classic PiStorm board and
runs the Macintosh IIci ROM on it: a 68040 to the Mac, memory on the Pi, a second screen on
the Pi's HDMI, disks on the Pi, WiFi, and the SE's own screen, keyboard, mouse, SCSI and
floppy kept. 0.3 is the first build meant for the hardware: a classic PiStorm (the DIP-64
board with the EPM240 CPLD, stock firmware) and a Raspberry Pi 3B, 3B+, 3A+ or Zero 2 W.

What has been tested: everything below runs in the project's testbed, where MAME stands in for
the SE's logic board and QEMU for the Pi (docs/08 item 28 on GitHub: System 7.1's Finder on the
SE's own screen, booted from the SE's SCSI disk). What has NOT been tested: the Pi talking to
a real CPLD and a real SE. This build is how that gets tested. Keep a serial cable on the Pi's
GPIO 14/15 (115200 8N1): the kernel's log is the only window into the first boots.

What is in the zip
------------------
  kernel8.img            Aurora68 itself (the Emu68 fork, build variant psmac)
  config.txt             the Pi firmware's settings: 64-bit kernel, the container, UART, HDMI
  cmdline.txt            the kernel's options: enable_cache debug mac.board=se bt=off mac.console=hdmi
  aurora68-512x342.declrom   the slot-9 declaration ROM for the SE's screen size: PiDisk,
                         Ethernet, WiFi, input and video drivers for the Macintosh
  aurora68.declrom       the same for a 640 by 480 second screen (the IIci testbed); and
  aurora68-WxH.declrom   one per larger HDMI screen size, 800x600 up to 1920x1200 (not for the
                         SE's screen yet)
  aurora68-wifionly.declrom   the WiFi as the only network card (MacTCP then takes the WiFi)
  aurora68-wifi.declrom  the screen with the WiFi as the only network card, for a Pi 3 alone; and
  aurora68-wifi-WxH.declrom   the same for each larger screen size
  get-firmware.sh        fetches every third-party file the card needs (the Pi's boot files, the
                         WiFi and Bluetooth firmware for every board), checks each one, and prints
                         the make-container.py line ("Setting up the SD card", step 2)
  make-container.py      builds aurora68.cpio from your ROM, the declaration ROM and firmware,
  patches/               and patches a stock IIci ROM on the way with the byte delta in patches/
                         (new in 0.3; 0.1 and 0.2 did not, which left System 7.1 to an occasional
                         zero divide at boot). Python 3 is all it needs; rompatch.py and
                         patches/iici.json are the source of that delta, for the record
  Mac/                   the Macintosh-side programs: PiMach, PiDisk (extensions), PiWiFi,
                         PiBlue, PiStatus, PiNet, PiPing, PiScreens, PiColor, PiLog (applications;
                         PiLog shows the Pi's log in a window, filtered by part), PiDepth (sets
                         the screen's depth at startup from the number in its name),
                         as MacBinary files and on Aurora68-Utilities.img (an HFS disk image)
  RELEASE-NOTES.md       what works, what does not
  LICENSES/              MPL-2.0 (Emu68, Aurora68) and GPL-2.0 (the Alice68 modules)

Setting up the SD card (a Pi 3B in an SE)
-----------------------------------------
  1. Format a microSD card as one FAT32 partition (any size from 1 GB).
  2. Put the Raspberry Pi firmware on it, and fetch the WiFi and Bluetooth firmware. The easy
     way: copy get-firmware.sh from this zip to the card's root folder and, from a terminal there
     (macOS or Linux; on Windows use WSL or the manual way below):

        sh get-firmware.sh

     It downloads the Pi's boot files into the card's root (for a Pi 3B, 3B+, Zero 2 W and Pi 4
     alike) and the WiFi and Bluetooth firmware of every board into wifi-firmware/, each from a
     fixed version and checked against its SHA-256, refuses anything too small to be firmware,
     and prints the make-container.py line for step 5. Run it again and it keeps what is already
     right. With your ROM beside it, "sh get-firmware.sh --container MacIIci_368CADFE.rom"
     makes aurora68.cpio as well. Nothing of Apple's is downloaded: the ROM and the system
     software are yours to supply. Then skip step 4.
     The manual way, from a terminal in the card's root folder:

        curl -fL --remote-name-all \
          https://raw.githubusercontent.com/raspberrypi/firmware/master/boot/bootcode.bin \
          https://raw.githubusercontent.com/raspberrypi/firmware/master/boot/start.elf \
          https://raw.githubusercontent.com/raspberrypi/firmware/master/boot/fixup.dat \
          https://raw.githubusercontent.com/raspberrypi/firmware/master/boot/bcm2710-rpi-3-b.dtb \
          https://raw.githubusercontent.com/raspberrypi/firmware/master/boot/bcm2710-rpi-3-b-plus.dtb \
          https://raw.githubusercontent.com/raspberrypi/firmware/master/boot/bcm2710-rpi-zero-2-w.dtb
        mkdir -p overlays
        curl -fL -o overlays/disable-bt.dtbo \
          https://raw.githubusercontent.com/raspberrypi/firmware/master/boot/overlays/disable-bt.dtbo

     (On Windows, curl.exe; the backslashes continue one command.) The .dtb for your board
     and the disable-bt overlay are needed: the kernel reads the device tree, and the overlay
     puts the PL011 serial port, where the kernel logs, on the header's GPIO 14/15.
  3. Copy everything from this zip to the card's root folder (the Mac folder can stay on your
     PC; its files go to the Macintosh, not the Pi).
  4. (Not needed after get-firmware.sh.) Get Broadcom's firmware for the Pi's WiFi (and
     Bluetooth, for later). In the same folder:

     Pi 3B (BCM43438):
        curl -fL --remote-name-all \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/cypress/cyfmac43430-sdio.bin \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/brcm/brcmfmac43430-sdio.txt \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/cypress/cyfmac43430-sdio.clm_blob \
          https://raw.githubusercontent.com/RPi-Distro/bluez-firmware/master/broadcom/BCM43430A1.hcd

     Pi 3B+, 3A+ (BCM43455):
        curl -fL --remote-name-all \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/cypress/cyfmac43455-sdio-standard.bin \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/cypress/cyfmac43455-sdio.clm_blob \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/brcm/brcmfmac43455-sdio.txt \
          https://raw.githubusercontent.com/RPi-Distro/bluez-firmware/master/broadcom/BCM4345C0.hcd

     (In that repository brcm/brcmfmac43430-sdio.bin and .clm_blob are links to the cypress files;
     the raw download of a link is a 31-byte path, not firmware. The sizes to expect: the .bin
     about 400 KB, the .clm_blob about 5 KB, the .txt about 1 KB, the .hcd about 30 KB.)

     Pi Zero 2 W (BCM43436):
        curl -fL --remote-name-all \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/brcm/brcmfmac43436-sdio.bin \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/brcm/brcmfmac43436-sdio.txt \
          https://raw.githubusercontent.com/RPi-Distro/firmware-nonfree/bullseye/debian/config/brcm80211/brcm/brcmfmac43436-sdio.clm_blob \
          https://raw.githubusercontent.com/RPi-Distro/bluez-firmware/master/broadcom/BCM43430B0.hcd

  5. Make the container, the one file the Pi firmware loads besides the kernel. Put your own
     Macintosh IIci ROM image (version 368CADFE, 512 KB; Apple's ROM is not included) next to
     make-container.py as MacIIci_368CADFE.rom and run (Python 3 needed), for a Pi 3B:

        python3 make-container.py -o aurora68.cpio MacIIci_368CADFE.rom \
          aurora68-512x342.declrom aurora68.declrom \
          cyfmac43430-sdio.bin brcmfmac43430-sdio.txt cyfmac43430-sdio.clm_blob BCM43430A1.hcd

     (for a 3B+/3A+, the cyfmac43455 files instead). The stock ROM is patched on the way; the
     output says so. The kernel also patches a stock ROM itself when it finds one in the
     container ("stock IIci ROM 368cadfe in the container: patched in memory ... verified" in
     the log), so an unpatched container works too. Copy aurora68.cpio to the card. The two declaration ROMs: the kernel takes
     the one whose name ends in the screen size in use, 512x342 on the SE board.
  6. Check cmdline.txt: one line, "enable_cache debug mac.board=se bt=off mac.console=hdmi".
     mac.board=se tells the kernel it is in a Macintosh SE and not in the testbed's IIci.
     mac.console=hdmi keeps the kernel's log on the HDMI screen for the whole run, the same text
     as the serial line, so a bench without a serial cable still sees everything; take it out
     to have HDMI show the Macintosh's picture instead (the log then shows until the
     Macintosh's video driver turns the screen on). To join a WiFi
     network at boot add wifi.ssid=NAME wifi.psk=PASSWORD wifi.country=XX (two letters).
     Memory: the kernel gives the Macintosh what the Pi can spare, up to 128 MB; mac.ram=N
     fixes it.
  7. The PiStorm: the classic board, with the firmware it came with. Remove the SE's 68000 (or
     use the socket if yours has one), seat the PiStorm with pin 1 where the 68000's pin 1 was
     (the notch end), the Pi on it. A full-size Pi 3B overhangs the board; make sure nothing
     under it touches the logic board.
  8. HDMI to a monitor if you have one (it shows the same 512 by 342 picture as the SE's screen
     in this build), the serial cable to GPIO 14 (TXD) and 15 (RXD), ground to 6. Power the SE.

A Pi on the bench, no SE yet
----------------------------
That is a useful first test. Power the Pi from USB with HDMI connected. The firmware's rainbow
square for a moment, Emu68's splash, then the log scrolling on HDMI (white on black, wrapping
to the top when it reaches the bottom). Expect "bridge=gpio", "protocol up" with whatever the
floating pins read, "board layer up", then either bus cycles that "complete" with junk or "the
CPLD did not finish a bus cycle ... is the Pi in a Macintosh?" and "TRANSPORT DEAD" in the
heartbeats: both are right for a Pi with nothing behind it. The "[WIFI]" lines are the ones that
matter on the bench: the chip id (a9a6 is a Pi 3B's 43430), "Cortex-M3 + SOCRAM", the firmware
loaded and running, a scan if wifi.ssid= is set. A photograph of the screen at a heartbeat is a
log. Nothing at all on HDMI, not even the rainbow square: the firmware did not start; look at
the green ACT LED (a repeating pattern of flashes is the firmware's error code: 4 means
start.elf not found, 7 kernel not found) and at the card (ejected properly, FAT32, files in the
root).

Booting System 7 on the bench, no SE at all (new in 0.4)
--------------------------------------------------------
The kernel can stand in for the whole logic board: with "mac.board=solo" it answers the VIA,
the clock chip, the ADB transceiver (no keyboard or mouse yet), the SCC, the floppy controller
(no drive) and a SCSI controller with a disk for each disk image in the container. So:
  1. Get a Macintosh hard disk image that boots System 7 on a IIci: an Apple-partitioned image
     with a driver partition and an HFS volume (what HD SC Setup or a Mac emulator makes). The
     file name must end in .img, .hda, .image or .hfv. Up to a couple of hundred megabytes on a
     1 GB Pi (it is loaded into memory with the rest of the container).
  2. Add it to the container: python3 make-container.py -o aurora68.cpio MacIIci_368CADFE.rom
     aurora68.declrom aurora68-512x342.declrom MyMac.img  (plus the WiFi files if you want the
     WiFi; the order does not matter). Copy aurora68.cpio to the card.
     For the network, use aurora68-wifi.declrom instead of aurora68.declrom: MacTCP takes the
     first network card it finds, and that file has only the WiFi one (a Pi 3 has no wired
     Ethernet). config.txt must say "initramfs aurora68.cpio 0x10000000" (0.4's does; with
     "followkernel" a large container lands in the kernel's early tables and the Mac shows the
     blinking question mark).
  3. cmdline.txt, one line: "enable_cache debug mac.board=solo bt=off" (no mac.console=hdmi:
     the log shows until the Mac's video driver takes the screen, then the Mac does). Add the
     wifi.ssid= / wifi.psk= / wifi.country= words if you like, and mac.screen=WxH for a bigger
     screen with the matching declaration ROM in the container.
     A Pi 3 at a bigger screen with the WiFi: the kernel now drives the Pi 3B's and 3B+'s wired
     port too, so the Mac gets both cards ("One card for a Pi 3 and a Pi 4" below); MacTCP takes
     the first, the wired one. On a Pi with no wired port (3A+, Zero 2 W) or with eth=off the
     kernel takes the wired card out of the declaration ROM by itself, so the ordinary
     declaration ROM of the screen's size will do; the WiFi-only ones (aurora68-wifi-WxH.declrom)
     say the same thing in the file. For a
     1080p monitor (hdmi_group=2, hdmi_mode=82 in config.txt, mac.screen=1920x1080 in
     cmdline.txt):

        python3 make-container.py -o aurora68.cpio MacIIci_368CADFE.rom \
          aurora68-wifi-1920x1080.declrom MyMac.img \
          cyfmac43430-sdio.bin brcmfmac43430-sdio.txt cyfmac43430-sdio.clm_blob BCM43430A1.hcd

     Put only one declaration ROM of each size in the container: with both
     aurora68-1920x1080.declrom and aurora68-wifi-1920x1080.declrom the kernel takes whichever
     comes last. The log says "the wired Ethernet card ($81) left out" when it hides the card.
     For a 1920 by 1200 monitor in millions of colours: in config.txt hdmi_group=2 and
     hdmi_mode=69; in cmdline.txt mac.screen=1920x1200; aurora68-1920x1200.declrom (on a Pi 3,
     aurora68-wifi-1920x1200.declrom) in the container in place of aurora68.declrom. On the Mac choose Millions in Monitors (32-bit
     addressing must be on; the solo board's parameter RAM has it on). The choice is kept in
     pram.bin on the card (below); PiDepth (in Mac/), renamed "PiDepth 32" in the System Folder's
     Startup Items, still sets it at every start if you prefer.
  4. Boot. The ROM's memory test takes a few seconds, the happy Mac appears, then "Welcome to
     Macintosh" and the Finder, about a minute on a Pi 3.
  5. Mouse and keyboard, over Bluetooth (new in 0.5). The kernel starts the Pi's Bluetooth unless
     cmdline.txt says bt=off; with bt.pair=1 (in the shipped cmdline.txt) it pairs with the first
     keyboard or mouse it finds in pairing mode and looks again every 20 seconds, so put the
     device in pairing mode any time after the boot. A keyboard shows a passkey in the log
     (mac.console=hdmi to see it): type it on the keyboard and press Return. Once paired, the
     kernel saves it in pairings.txt on the card and the device reconnects at every boot
     without pairing again. Classic Bluetooth and Bluetooth LE mice and keyboards both work.
     Or over USB (new in 0.7): plug a USB keyboard and mouse into the Pi 3's USB ports, before
     or after the boot. The Pi uses the first keyboard and the first mouse it finds. If they do
     not work, add usb=pio to cmdline.txt and send the [USB] lines of the log.
What the Mac writes to the image is written back into aurora68.cpio on the card a second or two
after the Mac stops writing (new in 0.5), so the next boot starts where the last one ended. Keep a
copy of aurora68.cpio somewhere else: a power cut in the middle of a write can damage the image,
as it would a real disk. Bluetooth pairings are kept in pairings.txt on the card, which the
kernel creates; the bt.dev= words in cmdline.txt still work and are read first. mac.card=ro or
mac.card=off in cmdline.txt stop the writing. Parameter RAM (new in the next release) is kept
in pram.bin on the card, as a real Mac keeps it in a chip with a battery: AppleTalk active in the
Chooser, the Network control panel's choice (Lagoon EtherTalk), Monitors' depth, the startup disk,
the sound. The kernel writes it a second after the Mac changes it, once the Finder is up, and reads
it before the Mac does at the next power-on; the clock goes on from where the last save left it.
mac.appletalk=1 and mac.xpram= still apply on top of it. Delete pram.bin to start from the
defaults. With
mac.board=se (the SE board) the same image appears as a PiDisk volume instead.

A Pi Zero W (the original, 2017) cannot run this: its processor is 32-bit only. The Zero 2 W can.

Booting fast (new in the next release)
--------------------------------------
In the SE the Pi is the processor: nothing happens on the Mac until the Pi's firmware has read its
files from the card, the kernel has set up, and the 68k starts. The firmware reads EVERYTHING in
the container before the kernel starts, at 10 to 20 MB a second on a Pi 3, so a container with a
100 MB disk image in it costs five to ten seconds of a dark SE. So:
  - The container holds only the ROM, the declaration ROM and the WiFi/Bluetooth firmware (about
    1 MB). For the SE:
        python3 make-container.py -o aurora68.cpio MacIIci_368CADFE.rom aurora68-512x342.declrom \
          cyfmac43430-sdio.bin brcmfmac43430-sdio.txt cyfmac43430-sdio.clm_blob BCM43430A1.hcd
  - A disk image goes on the card as a file of its own, beside aurora68.cpio, with a name ending
    in .hda, .img, .image, .hfv or .dsk (MyMac.hda; kernel8.img is never taken), or named in
    cmdline.txt with mac.image=NAME. The kernel finds it a moment after the 68k has started and
    reads it in the background while the Mac boots. In the SE it is the PiDisk volume; on the bench
    (mac.board=solo) it is the startup disk, SCSI ID 0, and what the Mac asks for is read first.
    What the Mac writes goes back into the same file. An image inside the container still works
    as before, and wins if there is one.
  - config.txt: boot_delay=0 (in this release's file). kernel8.img is gzip-compressed (1 MB
    instead of 5); the firmware inflates it itself. Optional: disable_splash=1 (a little faster,
    but the rainbow square is the sign that the firmware found its files) and, in the SE with HDMI
    at 640 x 480 or none, gpu_mem=16 with start_cd.elf and fixup_cd.dat copied from the firmware
    repository (smaller firmware; without those two files the Pi does not start).
  - cmdline.txt for the SE: "enable_cache mac.board=se" plus the wifi.* and bt.* words you use.
    mac.console=hdmi is fine: the log no longer holds the boot up.
  - The bench: the same container with the declaration ROM for your screen, the disk image
    on the card, "enable_cache mac.board=solo mac.screen=WxH ..." in cmdline.txt.
The kernel's log says how long each step took: "[BOOT] t=N.NNNs what", t counted from power-on.
The first line, "kernel entry", is the firmware's part. Please send those lines from your Pi.
The ROM's own start is shorter too: the IIci ROM's memory test (the Pi's memory cannot fail as
SIMMs do), its silent startup chime and its quarter-second wait at every empty SCSI ID are cut
short by the ROM patch the kernel and make-container.py apply.

One card for a Pi 3 and a Pi 4 (new in the next release)
--------------------------------------------------------
The same SD card boots a Pi 3B, a 3B+ and a Pi 4 (or 400): one kernel8.img picks its drivers by
board when it starts. Each board gets both its network cards on the Mac, the wired port and the
WiFi, side by side on the one slot-9 card:
    Pi 3B       wired: the LAN9514 on the Pi's USB    WiFi: BCM43438 (the *43430* files)
    Pi 3B+      wired: the LAN7800 on the Pi's USB    WiFi: BCM43455
    Pi 4, 400   wired: the Pi 4's own Gigabit (GENET) WiFi: BCM43455
    3A+, Zero 2 W   no wired port: the WiFi is the only card
What the card needs (get-firmware.sh fetches all of it): bootcode.bin, start.elf and fixup.dat
(the Pi 3's firmware), start4.elf and fixup4.dat (the Pi 4's), the device trees
bcm2710-rpi-3-b.dtb, bcm2710-rpi-3-b-plus.dtb, bcm2710-rpi-zero-2-w.dtb, bcm2711-rpi-4-b.dtb and
bcm2711-rpi-400.dtb, and config.txt with its [pi3] and [pi4] sections (this release's works for
both). The container holds every board's WiFi and Bluetooth firmware; the kernel takes the WiFi
set by the chip's id and the Bluetooth one by the board:

        python3 make-container.py -o aurora68.cpio MacIIci_368CADFE.rom aurora68-1920x1200.declrom \
          wifi-firmware/cyfmac43430-sdio.bin wifi-firmware/brcmfmac43430-sdio.txt \
          wifi-firmware/cyfmac43430-sdio.clm_blob wifi-firmware/BCM43430A1.hcd \
          wifi-firmware/cyfmac43455-sdio-standard.bin wifi-firmware/brcmfmac43455-sdio.txt \
          wifi-firmware/cyfmac43455-sdio.clm_blob wifi-firmware/BCM4345C0.hcd wifi-firmware/BCM4345C5.hcd

(the declaration ROM of your screen size: one with both network cards, not a -wifi- one). On the
Mac, Riptide uses both cards, en0 the wired one and en1 the WiFi, with DHCP on each and the
default route through the wired one while its cable is in (Riptide's own read-me: "Several
cards"). MacTCP can use one card only, the first: the wired one where there is one. In the
Network control panel Lagoon EtherTalk shows one icon per card, "Lagoon (9)" and "Lagoon Wi-Fi (9)".
Notes:
  - Bluetooth pairings belong to the Pi's Bluetooth chip as much as to the keyboard: one paired
    on the Pi 3 must be paired again on the Pi 4. pairings.txt keeps one key per device, so after
    moving the card back the Pi 3 may need the device paired once more too.
  - The card writer (pairings.txt, and the Mac's changes written back into the disk image on the
    card) works on a Pi 3 only so far: on a Pi 4 the kernel says "the Pi 4's card controller is not
    supported yet: nothing saved" and writes nothing. The image keeps the Pi 3's last state.
  - A Pi 4 does not fit the classic PiStorm board in the SE: a Pi 4 means the bench (mac.board=solo)
    or a different adapter.
  - The wired port on a Pi 3B or 3B+ has only been tested in the project's emulator (with a
    stand-in USB network device); the first real test is yours. The log lines to look for are
    "[ETH] LAN9514 found at USB address 2", "[ETH] MAC ...", "[ETH] link up, 100 Mbit/s full
    duplex", and every 15 seconds "[ETH]   LAN9514: running, link 100 full, rx ... tx ...".
    If the chip is not found the Mac's wired card refuses to open and the WiFi carries on;
    eth=off in cmdline.txt hides the wired card altogether.

What to expect, and what the log says
-------------------------------------
On the serial line, within a second: Emu68's banner, then "[PSMAC] options: ... bridge=gpio
(classic PiStorm)", "[PSMAC:GPIO] classic PiStorm protocol up ... RESET free", "[PSMAC:SE]
board layer up". Then the ROM runs: "[PSMAC] heartbeat" lines every five seconds with the bus
cycle counts. On the SE's screen: nothing for the first seconds (the memory test), the
startup chime from the SE's speaker is NOT expected yet (the ASC the ROM plays through is a
stand-in), then the grey desktop with the blinking disk if no startup disk is found, or the
"Welcome to Macintosh" from your SCSI disk.

If the log says "the CPLD did not finish a bus cycle ... is the Pi in a Macintosh?" the Pi is
not talking to the CPLD: seating, orientation, or the board's firmware. If the SE's screen
stays blank while the heartbeats show bus traffic, send the log: that is the SE's real timing
meeting a translation that has only met MAME's. Every finding goes into docs/08 on GitHub.

On the Macintosh
----------------
The drivers need no installation: they are in the declaration ROM. From Mac/, put PiMach and
PiDisk in the System Folder (System 6) or in Extensions (System 7) if you want them, and the
applications anywhere. Aurora68-Utilities.img is an HFS disk image with all of them.

Versions
--------
Emu68 1.1 line (upstream commit 61a61f7) with the psmac variant; Alice68 modules of 16
November 2026; MAME 0.264 for the testbed; QEMU 8.2.2. The source and the day-by-day account
are at https://github.com/farsonic/Aurora68.
